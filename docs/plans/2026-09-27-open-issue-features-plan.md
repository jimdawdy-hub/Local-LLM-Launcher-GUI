# Engine source updates and advanced placement controls

## Goal Capsule

Resolve open issues [#11](https://github.com/jimdawdy-hub/Local-LLM-Launcher-GUI/issues/11), [#13](https://github.com/jimdawdy-hub/Local-LLM-Launcher-GUI/issues/13), and [#15](https://github.com/jimdawdy-hub/Local-LLM-Launcher-GUI/issues/15) on the current `master` base (`55c42b1`). Provide an opt-in route to current source builds of vLLM and llama.cpp and usable controls for multi-GPU placement and CPU-resident MoE experts (mixture of experts: a model design that activates only selected expert subnetworks for each token). Keep existing installations and launches working. This plan covers these three features only; the other five open issues have separate bug work. Stop after resolving the eight open issues, before broader engine additions or flag-catalog expansion.

## Product Contract

### Summary and problem frame

The launcher recognizes installed engines and offers curated controls, but cannot update an engine from upstream source. Its llama.cpp UI exposes `--n-gpu-layers` and `--split-mode`, but no device list or per-card split proportions. Its freeform `extra_args` accepts lesser-known flags, yet gives no explanation or reliable hardware advice for them. Issue #15 links a [video](https://www.youtube.com/watch?v=VytSYCDhWQ0) whose ordinary upstream flag is `--n-cpu-moe`; its reported prefill speedup relies on code patches in a separate fork.

### Requirements

- R1 (#11). A user can deliberately start an update from the official vLLM or llama.cpp source and see preflight requirements, current/target revision, progress, logs, result, and an actionable failure explanation in Settings. No update starts on page load or application launch.
- R2 (#11). A failed or interrupted build leaves the prior engine usable. A running server keeps its existing executable. A successful build changes only future launches to the verified new executable. The app never overwrites an arbitrary user-managed installation or silently upgrades its own Python environment.
- R3 (#11). Update availability is explicit for supported environments; unsupported platform/backend combinations say why. A single update job runs at a time. No arbitrary repository URL, shell command, branch, or build flags enter the update API. Only a loopback client can request preflight or start an update, independently of the HTTP Host header.
- R4 (#13). For llama.cpp, users can choose participating devices and relative allocation across two or more GPUs, including a three-card equal split, and can still choose a single main GPU. The UI explains that `--tensor-split` takes proportions, not exact layer counts; `40,40,40` is an equal *weight share* request, not a guarantee of exactly 40 layers per card.
- R5 (#13). The launcher rejects malformed split settings before launch and explains the conflict. When custom placement is used, hardware advice must not imply exact per-card fit from pooled VRAM (video RAM, memory on graphics cards) alone. The UI must explain where the KV cache (conversation memory) goes for the selected split mode. Experimental `tensor` mode must warn about architecture support and reject disabled flash attention; quantized KV cache is allowed with an installed-engine compatibility warning; upstream disables automatic fitting in that mode.
- R6 (#15). Expose `--n-cpu-moe`, `--cpu-moe`, and `--ubatch-size` as documented, optional llama.cpp controls with plain-language tradeoffs. Existing `--no-mmap`, `--mlock`, `--n-gpu-layers`, `--batch-size`, and raw `extra_args` remain usable across old and new binaries. Explain that host RAM can reduce required GPU memory but may reduce throughput and is not a guarantee of fit.
- R7 (#15). The fork-only `GGML_CUDA_REGISTER_HOST` and `GGML_SCHED_PREFETCH_EXPERTS` optimizations are not presented as stock llama.cpp flags or silently set on ordinary builds. The video’s performance result is not promised by this launcher.
- R8 (#15). Offer llama.cpp's optional `--numa distribute`, `isolate`, and `numactl` choices (NUMA is non-uniform memory access: CPU sockets can reach their own memory faster than another socket's), with unset as the default. Separately offer an opt-in Linux `numactl --interleave=all` process wrapper for llama.cpp and native vLLM only. Show OS-visible node count and `numactl` availability; explain that one visible node has no cross-node distribution benefit. These controls must work for ordinary multi-node machines and must not be gated by whether this development machine is virtualized. Never change host NUMA policy automatically.

### Acceptance examples

- AE1 (R1–R3). Starting an eligible llama.cpp update shows source revision and live output; a simulated build failure keeps the previous `llama-server` path and new launches still use it. A successful build validates the executable and switches future launches only.
- AE2 (R1–R3). Starting an eligible vLLM update builds in an isolated environment; a failed install leaves the old `vllm` usable; unsupported OS/backend returns an explanatory response rather than running a guessed build recipe. A non-loopback API client cannot inspect or start an updater job even with an allowed Host header.
- AE3 (R4–R5). Three selected GPUs with `split_mode=layer`, `tensor_split=40,40,40` produce one `--device` and one `--tensor-split` option, with a visible note that the ratios are proportional and layer/KV placement is engine controlled. A two-value split for three selected devices is rejected.
- AE4 (R4–R5). `split_mode=none` with `main_gpu=1` builds the expected command and suppresses controls that imply multiple active cards. Custom split advice does not show an unqualified green fit based solely on summed VRAM. `tensor` with `flash_attn=off` is rejected with a reason; quantized K/V cache with on/auto is retained and allowed with an older-engine warning.
- AE5 (R6–R7). Setting `n_cpu_moe=26` yields `--n-cpu-moe 26`; `cpu_moe=true` yields `--cpu-moe`; the UI warns of RAM and throughput costs. On a newer binary, `no_mmap` alone becomes `--load-mode none`, `mlock` alone becomes `--load-mode mmap+mlock`, and both become `--load-mode mlock`; an old binary keeps the legacy flags. No fork-only environment variable appears in stock build commands.
- AE6 (R8). On a two-node Linux host, choosing llama.cpp `numa=distribute` emits `--numa distribute`; leaving it unset emits no NUMA flag. Enabling interleave prefixes the native llama.cpp or vLLM command with `numactl --interleave=all`, without a shell. Docker mode or missing `numactl` rejects that wrapper with a clear reason. On a one-node guest, the control is still discoverable but explains that distribution adds no benefit; no policy is enabled by default.

### Scope boundaries and assumptions

The first source-update implementation targets Linux with detected build prerequisites. llama.cpp can choose CPU or CUDA from detected tooling; native vLLM source building is offered only where its documented Linux GPU prerequisites are met. Existing Docker mode remains a separate installation path; no Docker image rebuild is required for #11. macOS/Windows show the existing manual installation guidance until tested build recipes exist. NUMA controls target OS-visible topology on any supported host, including bare-metal dual-socket systems; VM100's single visible node is only a test fixture, not a product limitation. Users may continue to use `extra_args` for other advanced flags. Do not add SGLang, Colibri, alternative forks, speculative decoding setup, arbitrary compiler option editors, or a universal flag browser in this issue pass.

## Planning Contract

### Current state and technical decisions

- KTD1. Extend the existing flag-catalog path: `src/local_llm_launcher/data/flags_llamacpp.json` drives `frontend/src/views/Launch.jsx` and `src/local_llm_launcher/engines/_args.py`. No second form schema or command builder is needed. Catalog defaults are display-only; new flags are emitted only when the user explicitly sets them. `extra_args` remains a fallback.
- KTD2. Implement #11 as **launcher-managed, isolated source builds** under the app data directory. Use fixed upstream repositories and resolve the offered target to an **immutable commit SHA before build**; report and build that same SHA even if upstream moves later. Use fixed official build recipes, a version-specific inactive directory, and an explicit user action. For llama.cpp, validate the built `llama-server` and then persist its path in the existing `llamacpp_path` setting. For vLLM, create a dedicated virtual environment (an isolated Python installation), follow the current official `uv pip install -e . --torch-backend=auto` source-build recipe inside a **permanent version-specific checkout** (editable installs refer to that path), validate its `vllm` executable, and persist a new `vllm_path` setting. Route that saved executable through the hardware availability probe, `api_launch`, `ServerManager.build_spec`, and `vllm_native.build` so native launches use it end to end; Docker mode remains unchanged. Check for `uv` and a suitable compiler rather than adding a launcher dependency or guessing that plain `pip install -e .` works. Never mutate system `pip`, a user clone, or an active executable. Activate the new path only after validation by changing settings; do not rename a working virtual environment or editable checkout. Retain the prior managed version for rollback until a later explicit cleanup. Do not build a version manager UI.
- KTD3. Treat source build as one background job with bounded, pollable output and an in-process concurrency guard, following the `DownloadManager` status pattern in `src/local_llm_launcher/downloads.py` while keeping build output in a log file. Before a job starts, check the CPU/GPU and toolchain version floors from current upstream docs, Git/CMake/compiler (`uv` and CUDA prerequisites for vLLM), writable disk space, supported OS, and whether the immutable target SHA is already active. Bound `MAX_JOBS` for vLLM and CMake build parallelism for llama.cpp to the available CPU/RAM; source builds can otherwise overwhelm a workstation. Use argument arrays with `subprocess`, never a shell command assembled from browser input. Guard every updater route by the actual client address being loopback; the existing Host-header middleware alone is insufficient. Expose no general command execution endpoint.
- KTD4. For #13, add `--device`, `--tensor-split`, and `--main-gpu` to the llama.cpp catalog and include `tensor` in current `--split-mode` choices. Prefer a small GPU-choice control populated from a capability probe (`llama-server --list-devices`) rather than assuming `nvidia-smi` indexes match all llama.cpp backend names. If probing fails, leave `--device` optional and show the engine's accepted format; never invent a mapping. Validate comma-separated positive finite split proportions, count against explicitly selected devices when known, and mode compatibility. Keep total GPU-layer count in `--n-gpu-layers`; explain that exact per-card layer counts are not guaranteed. `tensor` is experimental, requires flash attention; quantized KV cache is supported by current upstream builds (PR #23792), lacks upstream auto-fit, and is unsupported for several MoE/hybrid architectures; default to `layer`.
- KTD5. For #13/#15, change the advisor only where its current assertions become false: custom splits and MoE CPU offload receive an approximate/unknown-fit warning rather than an unearned green rating. Preserve useful total RAM and VRAM measurements, but do not subtract a guessed expert size or claim each card fits when model metadata cannot prove it. The launch command remains possible when there is no certain blocker.
- KTD6. For #15, use upstream llama.cpp flags only. `--n-cpu-moe` and `--cpu-moe` are mutually exclusive in the UI; `--ubatch-size` is an independent microbatch size (tokens processed together inside a batch). The video fork's two successful optimizations require patched source and are out of scope. The video also mentions speculative draft length, but that needs a draft model and benchmark context, so a standalone knob would mislead users.
- KTD7. Preserve the existing `no_mmap` and `mlock` UI values while building version-correct llama.cpp arguments. Probe the selected `llama-server --help` for `--load-mode`; when present emit exactly one mode: no-mmap only → `none`, mlock only → `mmap+mlock`, both → `mlock`, neither → no override. Otherwise emit the old flags as before. Do not pass old and new forms together; `--load-mode` is the current upstream option and recent builds remove the legacy forms. Cache or bound the help probe so opening the Launch view does not repeatedly spawn the binary. Keep mode handling in the llama.cpp builder, where the selected binary is known, rather than rewriting saved presets.
- KTD8. Add a nullable `numa` choice to the llama.cpp catalog and a shared, explicitly named `numactl_interleave` launch setting for native llama.cpp and native vLLM. Prefix native argv with `numactl --interleave=all` when selected and installed; reject the setting for vLLM Docker rather than wrapping the Docker client (which would not set the container's memory policy). Detect OS-visible NUMA nodes from Linux topology and the process's allowed-node mask, plus `numactl` on PATH. Do not infer physical socket count from VM100 or enable either policy automatically. `--numa numactl` remains an advanced engine choice for users who arrange CPU affinity externally; the interleave wrapper changes memory placement, not CPU affinity.

### Dependencies and sequencing

Implement U1 first, then U2/U3 (they both extend llama.cpp controls/advice), then U4. The active bug work must land before a full pytest run because [#9](https://github.com/jimdawdy-hub/Local-LLM-Launcher-GUI/issues/9) says the current API tests can mutate real settings. Base assumptions should be rechecked against the working tree immediately before execution, since the bug fixes are being made in parallel. The existing `master` at `55c42b1` has no updater; merged PR #14 addressed lifecycle/binding, not source updates.

## Implementation Units

### U1. Source-update job and safe engine selection (R1–R3; AE1–AE2)

- **Files:** `src/local_llm_launcher/updates.py` (new), `src/local_llm_launcher/api.py`, `src/local_llm_launcher/config.py`, `src/local_llm_launcher/hardware.py`, `src/local_llm_launcher/registry.py`, `src/local_llm_launcher/engines/vllm_native.py`, `frontend/src/api.js`, `frontend/src/views/Settings.jsx`, `tests/test_updates.py` (new), `tests/test_api.py`, `tests/test_engines.py`, `tests/test_hardware.py`.
- **Approach:** One fixed recipe per engine, no arbitrary execution inputs. Report preflight and revision before enabling update; run asynchronously with pollable log/status. Stage each version, verify executable, then update the relevant saved path. Continue using existing discovered binaries if no managed version exists. Keep the Settings UI limited to update/check/status/log/error.
- **Test scenarios:** Mock all subprocess/network operations: non-loopback client with a forged allowed Host rejected on every updater route; unsupported platform; CPU/GPU/toolchain floor unmet; already-current SHA; upstream moving after target SHA resolution does not change built revision; overlapping job rejected; bounded build parallelism; failed clone/build/install leaves path unchanged; successful validation changes the hardware probe and future native launch path through API → registry → builder; a running server retains its recorded argv; command arguments contain only fixed/upstream-derived values; vLLM managed executable is used only for native mode. Exercise API errors and status polling with isolated app data.

### U2. Explicit llama.cpp multi-GPU and NUMA placement (R4–R5, R8; AE3–AE4, AE6)

- **Files:** `src/local_llm_launcher/data/flags_llamacpp.json`, `src/local_llm_launcher/data/flags_vllm.json` for shared native-wrapper UI metadata if needed, `src/local_llm_launcher/engines/_args.py` only if catalog types require it, `src/local_llm_launcher/engines/llamacpp.py`, `src/local_llm_launcher/engines/vllm_native.py`, `src/local_llm_launcher/api.py`, `src/local_llm_launcher/hardware.py`, `src/local_llm_launcher/advisor.py`, `frontend/src/views/Launch.jsx`, `tests/test_engines.py`, `tests/test_advisor.py`, `tests/test_hardware.py`, `tests/test_api.py`.
- **Approach:** Use existing catalog controls where possible; make split ratios, device selection, and `--numa` discoverable and explain mode-specific KV placement. Detect visible NUMA nodes and `numactl` capability once per hardware refresh. Add one optional process wrapper for native engines, reject Docker use, and keep all NUMA behavior opt-in. Validate at the API/advisor boundary as well as in the form so direct API callers cannot bypass it. Show an approximate-fit warning for custom placement and a no-benefit explanation when only one node is visible.
- **Test scenarios:** Equal three-card ratios; uneven two-card ratios; selected-device count mismatch; empty/negative/nonfinite ratios; single-device `none` mode; invalid mode/ratio combination; no detected devices; tensor mode with flash attention off (reject) and quantized KV cache with on/auto (allow and preserve); tensor mode warning for known unsupported MoE architecture and disabled auto-fit; unsupported engine binary with a new flag reports its startup failure clearly. Confirm generated argv preserves each comma-separated value as one argument. Test zero/one/two OS-visible NUMA nodes (including an allowed-node mask), installed/missing `numactl`, unset/distribute/isolate/numactl choices, native llama.cpp/vLLM argv prefixes, and Docker rejection. Assert no automatic NUMA flag or wrapper on VM100-like one-node data.

### U3. Upstream MoE, microbatch, and NUMA advice (R6–R8; AE5–AE6)

- **Files:** `src/local_llm_launcher/data/flags_llamacpp.json`, `src/local_llm_launcher/engines/llamacpp.py`, `src/local_llm_launcher/advisor.py`, `frontend/src/views/Launch.jsx` only if mutual-exclusion display needs code, `tests/test_engines.py`, `tests/test_advisor.py`.
- **Approach:** Catalog entries for `--n-cpu-moe`, `--cpu-moe`, `--ubatch-size`, and the opt-in llama.cpp NUMA choices; bounds/help anchored to current upstream help. Translate the two legacy memory-loading toggles at command-build time using the selected binary's `--help`. Explain interactions with existing GPU layers and host RAM; distinguish CPU affinity from memory interleaving. Do not introduce fork flags or pretend the memory estimate knows exact expert tensor sizes.
- **Test scenarios:** Each flag is emitted only when set; mutually exclusive MoE settings are rejected; zero/default preserve engine automatic behavior; each of the four no-mmap/mlock combinations maps correctly on a new binary and uses legacy arguments on an old binary; no duplicate old/new loading arguments; offload advice warns that estimates are approximate; one-node NUMA advice says no distribution benefit while two-node data does not make the control automatic; no fork-only environment variables appear.
